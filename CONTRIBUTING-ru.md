Начните с [архитектуры](ARCHITECTURE-ru.md), чтобы понять контексты выполнения и потоки данных. При работе с агентом прочитайте `AGENTS.md`: он ведёт к общим ограничениям. Рабочие инструкции находятся в `.claude/skills`.

## Модульные тесты

Проект использует [Vitest](https://vitest.dev/) в качестве фреймворка модульного тестирования.

### Запуск тестов

```bash
# Запуск всех тестов
pnpm test

# Запуск тестов для конкретного файла
pnpm test entrypoints/common/storage/__tests__/tabListUtils.test.ts

# Запуск тестов с отчётом о покрытии
pnpm test:coverage
```

### Соглашения о файлах тестов

- Файлы тестов размещаются в каталоге `__tests__` рядом с исходным файлом, именуются `<модуль>.test.ts`.
- Покрытие охватывает утилиты и модули storage в `entrypoints/common/`.

```
entrypoints/common/storage/
├── tabListUtils.ts
└── __tests__/
    └── tabListUtils.test.ts
```

### Правила написания

- **Мокирование зависимостей**: используйте `vi.mock()` в начале файла для мокирования внешних зависимостей (например, `instanceStore`, `wxt/storage`), избегая зависимости от реального окружения.
- **Мокирование методов**: используйте `vi.spyOn()` для слежения или мокирования методов тестируемого объекта. Вызывайте `vi.restoreAllMocks()` в `afterEach` для очистки состояния.
- **Глобальные переменные WXT**: автоматически импортируемые WXT модули (такие как `storage`) необходимо мокировать через `vi.mock('wxt/storage', ...)`, а не через `globalThis`.
- **Независимые тесты**: сбрасывайте состояние моков в `beforeEach`, чтобы тесты не влияли друг на друга.

## Отправка кода

1. Сделайте [Fork](https://github.com/web-dahuyou/NiceTab/fork) репозитория.
2. Клонируйте свой форк локально.

   ```bash
   git clone https://github.com/${yourname}/NiceTab
   ```
3. Создайте ветку `dev-your-awesome-code` от `dev`.

   ```bash
   git checkout -b dev-your-awesome-code origin/dev
   ```
4. Зафиксируйте изменения (следуйте [соглашениям о сообщениях коммитов](https://github.com/angular/angular/blob/main/contributing-docs/commit-message-guidelines.md)).
  Перед коммитом рекомендуется выполнить `pnpm compile`, чтобы проверить типы TypeScript.

   ```bash
   pnpm compile
   git commit -m 'feat: 添加新功能'
   ```
5. Отправьте ветку в свой удалённый репозиторий.

   ```bash
   git push -u origin dev-your-awesome-code
   ```
6. [Создайте Pull Request](https://github.com/web-dahuyou/NiceTab/compare) из `dev-your-awesome-code` в ветку `dev` репозитория [web-dahuyou/NiceTab](https://github.com/web-dahuyou/NiceTab/compare/dev).

   ```bash
   https://github.com/web-dahuyou/NiceTab/compare/dev...${yourname}:NiceTab:dev-your-awesome-code
   ```

### Дополнительные правила коммитов

- Сохраняйте описанный выше процесс: fork, ветка от `origin/dev`, push в собственный `origin` и PR в `dev` основного репозитория. Дополнительный remote `upstream` не требуется.
- Заголовки коммитов проекта имеют вид `<type>: <описание на китайском>` или `<type>(<scope>): <описание на китайском>`. Типы: `feat`, `fix`, `perf`, `docs`, `style`, `refactor`, `test`, `build`, `ci`, `chore`. Сверяйтесь с недавними записями `git log`.
- Перед коммитом проверьте рабочий и staged diff. Включайте только файлы или фрагменты задачи, сохраняя остальные незакоммиченные изменения. Агент выполняет commit и push только в пределах разрешения пользователя.
- В PR опишите проблему, итоговое поведение, область влияния и проверки. Для UI при необходимости приложите снимки экрана и укажите непроверенные сценарии.

## Правила разработки

### Настройка проекта
- Установка зависимостей:
  `pnpm install`
- Запуск dev-сервера:
  `pnpm run dev`

### Обязательный export

Скриптовые точки входа WXT используют `export default defineBackground(...)`, `defineContentScript(...)` или соответствующее определение. Обычные общие модули и подключённые из HTML файлы `main.tsx` не обязаны иметь default export. Проверяйте расположение новых файлов, чтобы WXT не принял общий модуль за отдельную точку входа.

### Алиас путей импорта

Для межмодульных импортов предпочитайте алиас `~`, который указывает на корень проекта. Алиас `@` также работает, но для единообразия используйте `~`. Внутри каталога допустимы относительные пути.

```ts
import { something } from '~/entrypoints/common/utils';
```

### Путь к бинарникам браузера

По умолчанию `WXT` пытается сам найти установленные `Chrome/Firefox`. Если появляется ошибка:

```
ERROR  No Chrome installations found.
```

или нужно указать свой исполняемый файл браузера, см. [документацию — Set Browser Binaries](https://wxt.dev/guide/essentials/config/browser-startup.html#set-browser-binaries).

```js
// <rootDir>/web-ext.config.ts

import { defineRunnerConfig } from 'wxt';

export default defineRunnerConfig({
  binaries: {
    chrome: '/path/to/chrome-beta', // Chrome Beta вместо обычного Chrome
    firefox: 'firefoxdeveloperedition', // Firefox Developer Edition вместо обычного Firefox
    edge: '/path/to/edge', // MS Edge при запуске "wxt -b edge"
  },
});
```

### Сохранение данных пользователя

Чтобы сохранять данные между сессиями разработки, следуйте [официальной документации — persist-data](https://wxt.dev/guide/essentials/config/browser-startup.html#persist-data).

```js
// <rootDir>/web-ext.config.ts

import { defineRunnerConfig } from 'wxt';

// Mac/Linux
export default defineRunnerConfig({
   chromiumArgs: ['--user-data-dir=./.wxt/chrome-data'],
});

// Windows
import path from 'path';
export default defineRunnerConfig({
   // В Windows путь должен быть абсолютным
   chromiumProfile: path.resolve('.wxt\\chrome-data'),
   keepProfileChanges: true
})
```

Конфигурации Mac/Linux и Windows выше являются альтернативами. Выберите вариант для своей ОС и оставьте только один `export default` в файле конфигурации.

## Окружение и запуск

Используйте pnpm и `pnpm-lock.yaml` из репозитория. Корневой `package.json` указывает Node.js `>=18.20.0`, но текущие зависимости, включая `marked` и `happy-dom`, требуют Node.js `>=20`. Окружение должно удовлетворять и требованиям зависимостей; корневая декларация не гарантирует работу всех инструментов на Node 18. Зависимости и команды определены в `package.json` и lock-файле.

```sh
pnpm install
pnpm dev
# Firefox
pnpm dev:firefox
```

Скрипт `postinstall` запускает `wxt prepare`, создавая конфигурацию типов `.wxt`, которую наследует `tsconfig.json`. Не редактируйте сгенерированные файлы `.wxt` вручную. Если зависимости уже установлены, а конфигурации нет, выполните `pnpm exec wxt prepare`.

`dev:firefox` сейчас передаёт `--mode production`, поэтому его режим отличается от `dev`. Скрипты запуска, сборки и упаковки сначала выполняют `convert:guide`, который может обновить HTML руководства. Проверяйте diff, чтобы не включить посторонние сгенерированные файлы.

## Запуск браузера и локальные данные

`web-ext.config.ts` настраивает локальный запуск; сейчас данные Chromium для разработки сохраняются в `.wxt/chrome-data`. Если браузер не найден, задайте подходящие `binaries` локально. Агенту по-прежнему нужно подтверждение перед изменением конфигурации. Не включайте личные абсолютные пути к браузерам в общие настройки.

Профиль разработки может содержать реальные вкладки. Для проверки удаления, импорта с перезаписью, удаления после восстановления и синхронизации используйте временные данные. Разрешения, сочетания клавиш и особенности манифестов заданы в `wxt.config.ts`.

## Правила кода

Следуйте этим соглашениям. Точные настройки форматирования и линтера находятся в `.prettierrc` и `eslint.config.js`.

- **Формат и область изменений:** отступ — два пробела, точки с запятой, одинарные кавычки и завершающие запятые. Следуйте соседнему коду и форматируйте только изменённые участки. ESLint сейчас не требует сортировки импортов; не переупорядочивайте весь файл без необходимости.
- **Имена и типы:** PascalCase для React-компонентов, префикс `use` для хуков, camelCase для переменных и функций. Для констант и enum сохраняйте стиль модуля. Общие доменные типы размещайте в `entrypoints/types/`, локальные — рядом с использованием; предпочитайте `import type` для типов. Явно типизируйте новые интерфейсы, не обходите ошибки через `any` или приведение типов.
- **Импорты и экспорты:** для межмодульных импортов предпочитайте корневой алиас `~`, например `~/entrypoints/common/storage`; внутри каталога допустимы относительные пути. Скриптовые точки входа WXT используют `export default defineBackground(...)`, `defineContentScript(...)` или соответствующее определение. Обычные модули и подключённые из HTML файлы `main.tsx` не обязаны иметь default export. Не добавляйте бессмысленные экспорты; размещайте новые файлы так, чтобы WXT не принял их за отдельные точки входа.
- **React и стили:** сохраняйте существующие подходы с функциональными компонентами, hooks, Ant Design и styled-components. Соблюдайте порядок вызова хуков, очищайте подписки и таймеры в effect. Проверяйте зависимости и замыкания, даже если соответствующее правило линтера отключено. Используйте значения темы и соответствующие `*.styled.tsx` или существующие файлы стилей. Сохраняйте изоляцию Shadow DOM в content scripts.
- **Данные и побочные эффекты:** UI обращается к экземплярам из `entrypoints/common/storage/`, не обходя значения по умолчанию, миграцию, объединение и корзину. Повторно используйте `tabs.ts`, API `browser.*` и проверки возможностей/разрешений. Постоянные ID данных не равны ID вкладок браузера.
- **Сообщения и обновление:** учитывайте локальную отрисовку и уведомления других контекстов. Mitt и React Context не работают между окнами. Для новых runtime-сообщений согласованно обновляйте типы, отправителей и получателей; см. `.claude/skills/nicetab-dev/references/messages.md`.
- **Бизнес-ограничения:** сохраняйте поведение промежуточной области, блокировок, порядка закреплённых групп, удаления дублей и обработки неудачных операций; см. `.claude/skills/nicetab-dev/references/checklist.md`. Не описывайте непроверенный замысел как реализованную гарантию.
- **Тексты и логи:** пользовательские тексты храните в ресурсах локализации. Сохраняйте полезную обработку ошибок и диагностику, не записывая секреты в логи. Перед удалением добавленных логов агент следует правилу подтверждения. Для дат в именах файлов предпочитайте существующий подход dayjs и `YYYY-MM-DD_HHmmss`.

## Локализация и документация

UI-ресурсы находятся в `entrypoints/common/locale/modules/`: `zhCN.ts`, `zhTW.ts`, `enUS.ts`, `ruRU.ts`. При изменении ключей синхронизируйте все четыре языка, включая параметры и смысл ICU-выражений. В React используйте существующий `useIntlUtls().$fmt`, вне React — утилиты локализации. Строки манифеста отдельно хранятся в `public/_locales/`.

Сохраняйте одинаковый смысл, команды и ссылки в существующих переводах документов; не добавляйте новые языки по умолчанию. Термины и порядок работы описаны в `.claude/skills/translate/SKILL.md`. Вручную ведите только `CHANGELOG-zh.md` и `CHANGELOG.md`; соответствующий HTML и `.output` создаются генерацией.

Скрипт `scripts/md2html.js` преобразует документы в статический HTML для расширения. Сохраняйте существующие блоки переключения языков `<p>` / `<a>` со ссылками на `.md` в том же каталоге. Скрипт также распознаёт Markdown-ссылки, но помещает результат в один каталог, не копируя исходники и не сохраняя вложенную структуру документов. Для исходников и внутренних материалов агентов указывайте пути в репозитории, чтобы файлы с именем `SKILL.md` не перезаписывали друг друга. Проверяйте преобразование копией скрипта во временном каталоге и проверяйте ссылки языков; не редактируйте сгенерированный HTML вручную.

При описании существующих функций опирайтесь на закоммиченные исходники HEAD, а не на staged или незакоммиченные изменения. Наличие коммита не означает выпуск версии. Для документации разрабатываемой функции явно согласуйте область и статус.

## Проверка и сборка

Выбирайте проверки по области влияния и указывайте в PR результаты и непроверенные сценарии:

| Команда                                  | Назначение                           |
| ---------------------------------------- | ------------------------------------ |
| `pnpm compile`                           | Проверка типов TypeScript            |
| `pnpm lint:no-fix`                       | ESLint без автоматических изменений  |
| `pnpm test <путь-к-тесту>`               | Связанные существующие тесты         |
| `pnpm test`                              | Все тесты Vitest                     |
| `pnpm test:watch` / `pnpm test:coverage` | Режим наблюдения / отчёт о покрытии  |
| `pnpm build` / `pnpm build:firefox`      | Сборка Chromium / Firefox            |
| `pnpm zip` / `pnpm zip:firefox`          | Пакеты для соответствующих браузеров |

`pnpm lint` исправляет файлы; заранее проверьте область изменений. Для правок только документации достаточно проверить пути, ссылки, Markdown и согласованность переводов. Агент не добавляет тесты к новым функциям без явного запроса; при таком запросе следуйте `.claude/skills/unit-test/SKILL.md`.

Тесты размещаются в соседних каталогах `__tests__/` с именами `*.test.ts` или `*.test.tsx`. Vitest интегрируется с WXT через `WxtVitest()`; покрытие задаётся в `vitest.config.ts`. Моки браузера не заменяют проверку в реальном браузере.

При изменении UI или API браузера вручную проверяйте затронутые панели управления, popup и content scripts в соответствующих сценариях Chromium/Firefox. Для обновления данных проверьте панель в другом окне, для сохранения — повторное открытие страницы. Синхронизацию проверяйте на тестовых серверах: объединение, перезапись, сообщения об ошибках и включение синхронизации настроек.
